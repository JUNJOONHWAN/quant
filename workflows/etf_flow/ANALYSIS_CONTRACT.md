# ETF Flow Hermes Analysis Contract

## Scope

The completed ETF Flow source package is immutable input. The collection source
may still be generated by legacy runtime code in `STOCK`, but it is first
hash-verified and copied into `quant/workflows/etf_flow/data/`. All packet
building, news enrichment, analysis artifacts, and dashboard exports read only
the staged `quant` copy. This workflow does not recollect, patch, zero-fill,
or infer missing source data.

The analysis owner is the DGX `quant` project. Interactive analysis production
may use the Hermes `quant-market-analysis` skill and its configured market MCP
servers; `STOCK` remains the runtime and legacy collection source. Routine cron
publication is model-independent and never invokes Hermes, vLLM, or another
writer model.

## Inputs

- `massive_flows.json`: ETF flow series and observed sessions
- `fmp_quotes.json`: price, change, volume, and average volume confirmation
- `analyst_estimates.json`: consensus context
- `barchart_qqq.json`: QQQ options context
- `output/etf-flow-report-YYYY-MM-DD.md`: daily-report continuity history

The packet builder validates the complete 31-ETF universe, all four sources,
and the nine QQQ option metrics. A missing source is a hard failure, not a
fallback case.

## Prompt Matrix

The accepted analysis artifact answers six bounded questions, each with
evidence and limitations:

1. Flow structure
2. Price and volume confirmation
3. Options risk map
4. Rotation and defense
5. Change from daily reports
6. Weekly continuity

An interactive seventh synthesis prompt produces the market statement,
mood-change status, and weekly-continuity status. It may use only the packet and
the six verified section responses. Before the six questions, an interactive
news-enrichment prompt may use the DGX market-analysis MCP route, store article
URLs and published times, and report source coverage as confirmed, partial, or
failed.

## Output And Coverage Rules

The final `analysis.json` records source status, prompt questions, per-section
answers, a market statement, the daily-report comparison, observed flow
sessions, report coverage, and all limitations.

The workflow never fills a missing daily report or flow session. If the latest
seven calendar days have incomplete report coverage, Hermes must state it and
the weekly conclusion cannot be presented as a complete seven-day assessment.

## Candidate Strategy Registry

Routine refreshes run only the model-independent `primary` publication gate.
They publish an already accepted analysis bound to the current packet bytes, or
rebind a prior accepted analysis only when a normalized semantic packet digest
matches exactly. Reused news is marked `partial` with its source report date.
When no accepted semantic match exists, the cron exits immediately with
`analysis_required`; it does not invoke Hermes or wait for a vLLM model.

Interactive analysis can use the following registered strategies. The
alternatives are prepared in advance but are not run in parallel:

- `evidence_editor`: replaces an answer rejected for language quality, evidence
  phrasing, or unsupported session wording.
- `conservative_editor`: replaces an answer that overstates a directional
  conclusion when coverage or timing is incomplete.
- `coverage_editor`: replaces an answer whose chronology, report coverage, or
  data-lag explanation is unclear.

Each alternative reads the same accepted quant packet, accepted news links, and
primary artifact. It must preserve the exact six sections, evidence values,
and coverage facts. No lower-quality cache or hardcoded text can be published.

Review feedback records the rejected strategy, rejection reason, selected
alternative, and artifact path. The record is the input for adding a new
strategy when an existing option cannot meet the contract.
